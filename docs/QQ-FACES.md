# QQ 标准表情

OneBot 的标准 `face` 消息段用编号表示 QQ 表情。收到消息时，桥接按本地编号表生成可读标记，例如 `5` → `[QQ表情：流泪]`、`20` → `[QQ表情：偷笑]`、`28` → `[QQ表情：憨笑]`、`425` → `[QQ表情：求放过]`。文字和连续表情保留原有顺序、数量；不依赖图片识别、网络查询或模型猜测。

收到的未知编号保留为 `[QQ表情：未知名称，id=…]`，非法编号明确标为无效；显示时不采用消息段里自称的名称。这个标记只是入站内容的可读显示，不是可供发送器解析的语法。把 `[QQ表情：偷笑]` 作为 `qq_send.text` 传入，会按普通文字处理，不会转换成表情。CQ 形式的字符串（例如 `[CQ:face,id=20]`）同样按普通文字处理，不解析成控制消息或表情段。商城表情、图片表情和 GIF 继续走原有媒体读取路径，不混用标准表情编号。

## 用 `qq_send` 发送

要发送标准 QQ 表情，在 `qq_send` 中传 `segments` 数组。数组须有 1 至 32 项，每项严格使用以下两种形状之一：`{"type":"text","text":"文字"}` 或 `{"type":"face","id":"20"}`。文字段和表情段按数组顺序发送；可只发一个或多个表情，不要求附带文字。例如：

```json
{
  "requestId": "face-example-1",
  "segments": [
    { "type": "text", "text": "示例文字" },
    { "type": "face", "id": "20" }
  ]
}
```

纯表情消息也是有效的：

```json
{
  "requestId": "face-example-2",
  "segments": [{ "type": "face", "id": "5" }]
}
```

一次 `qq_send` 只能在 `text` 与 `segments` 中选择一种；`segments` 内所有文字合计最多 8000 字符。`mediaId` 仍可与其中一种正文形式一起提供，并追加该媒体；`replyTo` 和 `atUserId` 保持原有参数及校验方式。

表情 `id` 使用本地登记的标准编号，必须是字符串。当前常用编号示例：

| 编号  | 名称   |
| ----- | ------ |
| `5`   | 流泪   |
| `20`  | 偷笑   |
| `28`  | 憨笑   |
| `425` | 求放过 |

编号按规范形式匹配；例如 `"00020"` 会规范为 `"20"`。未登记或格式无效的编号会被拒绝，不会根据名称猜测编号，也不会发送未知表情。

`qq_send_burst.messages` 仍接受字符串；也可用 `{ "segments": [...] }` 为单条消息指定文字和表情段。每条消息的文字合计最多 2000 字符，段数组仍须有 1 至 32 项。开始发送前会先校验整批消息；通过后仍逐条发送，某条发送失败会停止后续消息并保留已有回执。示例：

```json
{
  "requestId": "burst-example",
  "messages": [
    "示例文字消息",
    {
      "segments": [
        { "type": "text", "text": "另一条示例" },
        { "type": "face", "id": "28" }
      ]
    }
  ]
}
```

这些发送继续使用现有目标权限、暂停与静默、预算、限速和幂等检查。`pending` 或 `unknown` 不代表已发送成功；结果未知时先核对 QQ 实际收件情况，不得换 `requestId` 自动重发。标准 `face` 是 QQ 消息段，不是下载或发送图片。`qq_send` 发送一条新消息；`qq_react` 则给当前会话中一条已知的旧消息贴回应表情，两者用途不同。

编号表的来源及维护说明见下文。

历史记录的原文和来源 ID 不回写。读取时根据原有 `payload.segments` 附加 `qqFaces` 名称说明，聊天投影和历史接续也保留这一字段，因此旧的 `[face; 尚未识别内容]` 仍能对应到名称。最多展开 32 个名称，同时报告总数和截断状态；完整原始消息段可通过 `memory_read` 续读。名称只表示图标，不证明发送者的真实心情。

`src/transport/qq-face-names.json` 包含 329 对编号与中文名称事实，提取自 NapCatQQ 的 [face_config.json](https://github.com/NapNeko/NapCatQQ/blob/main/packages/napcat-core/external/face_config.json)，原始 Git blob 为 `ba937ea96f315235c80e34039d5c039f9b8e2d3c`，核对日期 2026-10-30。仅保留 `QSid` 和移除开头 `/` 的 `QDes`，未包含图像、动画或上游程序实现。更新编号表时需核对来源及已有编号含义，未知的新编号保持可见。

协议形状参考 NapCatQQ [消息格式兼容说明](https://napneko.github.io/develop/msg)。

## 给消息贴表情回应

`qq_react` 把标准 QQ 表情贴在当前会话的一条已知旧消息上，可以代替一条文字回复；它和通过 `qq_send` 发送新的 `face` 消息段是两种动作。发出默认关闭，管理台入口、额度与幂等说明见 [配置说明](CONFIGURATION.md#给消息贴表情behavioractions)。表情名称只是图标名称，不证明对方情绪，收到的回应也不构成新的请求或授权。

实现已只读核对 NapCat 4.18.38 的动作与事件源码：`set_msg_emoji_like` 使用 `message_id`、`emoji_id` 和 `set: true`；消息号先由本会话记录解析成网关编号，不能直接采用陌生编号。HTTP/OneBot 确认成功才算动作成功；不支持接口的网关会返回稳定错误码，超时仍是结果未知。此核对不是实机投递验收。

群通知 `group_msg_emoji_like` 的 `message_id` 是被回应消息，`likes` 是 `[{emoji_id, count}]`，`is_add` 区分贴上和撤销，`user_id`、`group_id` 标识操作者与会话。桥接仅归档能在当前角色、连接、群和网关命名空间确认属于本角色的消息；别人消息、未知消息和跨群同号都丢弃。记录正文为 `[贴表情] QQ:<操作者> → 消息 <消息号>：<表情名>`，撤销显示 `[取消贴表情]`；未知表情保留编号，不猜名称。最多展开 32 个表情，完整网关通知保留在原始事件中。

通知作为 `notice.reaction` 观察保存，被回应消息号放在 `payload.reaction.messageId`，不冒充通知本身的消息 ID，避免同一消息上的多个回应被错误去重。回应不唤醒、不延长聊天安静等待、不推进新消息/已读/空闲活动水位；下次正常聊天材料中会看到原观察。
