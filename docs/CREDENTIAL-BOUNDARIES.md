# 第二轮：审批标识与子进程凭据边界

本轮移除管理台状态中的模型 capability，并收紧 Codex 与管理台原生 QQ 子进程默认继承的环境变量。原有暂停、白名单、工具权限、来源保护、精确外发授权及专属 Codex 登录目录继续生效。

## 审批接口

`GET /api/status` 的 `disclosureRequests` 不再包含 `token`，改为独立随机 `approvalId`。它只标识一个待审批项目，不能作为 `/agent/tools` 或 `/agent/catalog` 的 capability；批准仍要求管理员认证。旧页面或使用旧 `token` 请求格式的客户端需刷新或升级，服务端不保留旧格式的兼容入口。

`POST /api/disclosure` 使用以下结构：

```json
{
  "approvalId": "从状态接口原样取得的审批 ID",
  "agentId": "agent-a",
  "conversation": "group:20000",
  "ids": ["从状态接口原样取得的完整资料集合"],
  "requestId": "仅外部请求需要，原样回传状态中的精确请求摘要"
}
```

服务端在当前有效上下文中查找该 ID，再核对角色、会话、有效期、完整资料集合及外部请求摘要。权限撤销、暂停、重置会话、回合结束、资料集合变化或待审批动作被替换后，旧审批不可使用。批准后消耗审批 ID，重复提交不会增加授权。同一待批准动作的重复失败不会不断生成新 ID；待审批项目随上下文回收，不持久化 capability 或审批映射。

外部请求参数在提出审批时复制，后续修改调用方对象不会改变管理台展示内容。批准后仍执行原有“当前回合、精确参数与来源集合”的外发检查；变更查询、工具或来源需要重新授权。审批的一次消费不把已有工具契约改为“一次网络执行”：同一回合相同精确读请求仍按原有规则处理。QQ 运维资料披露继续使用当前角色、会话和资料集合的授权语义，不新增通用发言权限。

## 子进程环境

`buildChildEnv` 为 Codex 和管理台原生 QQ 构造环境；未列入白名单、也未明确映射的父进程变量均不传入。

| 类别           | 默认处理                                                                                                                                                              |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 基础运行       | 保留 PATH、HOME、用户/登录名、SHELL、临时目录、终端、时区及常用语言/locale 变量                                                                                       |
| 网络           | 保留 HTTP/HTTPS/ALL/NO_PROXY 的大小写形式及 SSL_CERT_FILE、SSL_CERT_DIR、NODE_EXTRA_CA_CERTS；这些是目标进程的网络运行配置，代理 URL 自带的认证信息也会随代理配置传递 |
| Windows        | 补充系统目录、命令解释器、扩展名查找、用户 profile、AppData 和程序目录；变量名按不区分大小写处理，输出去重，冲突的显式映射拒绝启动                                    |
| Linux 原生 QQ  | 保留 DISPLAY、Wayland、XDG 目录/会话、XAUTHORITY 和桌面 D-Bus 地址等 GUI 启动变量；Codex 默认不获得桌面会话变量                                                       |
| macOS 原生 QQ  | 保留 `__CF_USER_TEXT_ENCODING`                                                                                                                                        |
| 凭据及执行注入 | GitHub、OneBot、TOTP、其他模型/API 密钥、SSH agent、NODE_OPTIONS、LD_PRELOAD、DYLD 注入变量等默认不继承；只有管理员明确映射的变量可以加入                             |

Codex 仍由桥接固定设置数据目录内的 `codex/<agentId>/home` 为 CODEX_HOME。父进程日常 Codex home 不继承，显式映射也不能覆盖该目录。新增可选 `backends[].env`，仅用于 Codex；未配置时不改变旧配置结构。例：

```json
{
  "id": "codex-role-a",
  "type": "codex",
  "label": "独立 Codex",
  "env": {
    "ROLE_SERVICE_KEY": "QQ_ROLE_A_SERVICE_KEY"
  }
}
```

映射含义为“子进程变量名 → 桥接父进程中的变量名”，配置中只保存名字。它不是新的登录机制：专属实例原有的登录检查仍然执行。相同 backend 配置被多个角色使用时，其显式映射也会共享；需要不同凭据时应使用不同 backend 配置。新映射凭据同时纳入已有外部请求的凭据拦截检查。

管理台原生进程沿用 `connections[].process.env` 的同种映射。源变量缺失或为空会在启动子进程前失败，分别报告 `CODEX_ENV_MISSING` / `PROCESS_ENV_MISSING`。所需的自定义启动变量现在必须显式登记，不能依赖全量继承。修改映射后需重建相应进程才能更新环境。

独立 macOS QQ 启动器 `scripts/lib/local-process.mjs` 原本已有环境白名单及按 profile 注入的 NAPCAT 变量，本轮保留其策略。外部 MCP 也保留 SDK 的安全默认环境与既有显式映射，不转用新的通用白名单。

环境裁剪降低意外凭据传递，不是操作系统文件隔离；HOME、配置文件、已授权工具和管理员自定义启动器仍按其原有边界工作。没有更改 QQ 登录目录、专属 Codex 登录内容或部署配置。

## 验证与升级

HTTP 回归覆盖：状态与导出不包含 capability、审批 ID 不能调用模型工具、管理员认证、过期/撤销/重置、角色/会话错配、资料及动作变化、重复批准、原有精确授权及真实管理台脚本提交格式。

环境回归使用合成密钥、临时目录和离线协议替身，实际启动 Node 子进程验证 Codex RPC、原生进程与外部 MCP 的环境边界，并验证专属登录目录检查和显式映射。Windows/Linux/macOS 的变量选择另以合成环境测试；这些测试不等同于三个平台上实际安装的 QQ/Codex 或真实代理、证书链验收。

部署新版后刷新管理台；如果此前依赖隐式继承的专用变量，先登记相应映射再启动目标进程。生产重启、真实 QQ 登录与出站、真实模型和平台启动验收需独立安排。本轮无数据库 schema 迁移，不删除或轮换现有凭据。
