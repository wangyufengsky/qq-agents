# 版本更新

管理台「系统 → 版本更新」显示当前安装版本、提交、官方稳定版和发布说明。点击「立即检查」访问官方 GitHub Releases；同一分钟内重复点击会复用结果。「忽略此版本提醒」只隐藏该版本的提醒，仍能查看说明或恢复提醒。

自动检查默认关闭。开启后每 6 小时检查一次；网络失败采用 5 分钟起的退避，最长 6 小时。检查仅请求公开发布信息，不发送配置、账号、聊天、记忆或角色的 GitHub 凭据。无法连接时保留上次成功结果并标明失败，不会误报“已经是最新版”。设置保存在数据目录的 `updates.json`。

只比较正式版本号。版本号相同可能对应不同提交，开发分支、本地修改版、提交未知的安装都要核对实际代码，不能仅凭版本号覆盖或降级。预发布版不进入稳定更新渠道。

## 本机源码安装

1. 记录当前代码提交、启动方式、数据目录以及全局、角色和会话的暂停状态。保留本地代码改动。
2. 正常停止桥接，保留完整数据目录备份。SQLite 备份可用 `npm run memory:backup`，但它不包含配置、凭据、媒体和模型 home；详见 [迁移与备份](MIGRATION.md)。
3. 在独立代码目录检出所选正式发布标签，用 `npm ci --ignore-scripts` 安装依赖。不要覆盖正在运行的代码目录。
4. 使用原数据目录和原启动参数启动新版。先保持全局暂停，检查管理台、QQ 连接和各角色后端，再恢复原先允许运行的角色。

数据库发生迁移时，回退代码必须搭配升级前的兼容备份。恢复发言后产生的新聊天和发送账本不能直接用旧备份覆盖；需要停机评估与人工恢复，防止丢记录或重复发言。

## Docker

在宿主机操作，按 [Docker 升级与备份](DOCKER.md#升级与备份) 先停机备份数据卷，再更新到目标标签并构建容器。保留旧镜像和数据备份。管理台容器不挂载 Docker socket，也不修改宿主机其他容器。

## 启用一键升级

本机先正常停止原来的桥接，保留原来的数据目录和运行参数，再改用独立启动器：

```sh
npm run managed -- --data /path/to/data
# 原来在 live 模式运行且希望启动后恢复连接：
npm run managed -- --data /path/to/data --live --resume
```

启动器接管桥接进程，管理台「一键升级」会显示可用状态。自动检查仍需单独开启；发现更高的正式版本后，点击「备份并升级」并核对目标版本。普通 `npm start` 仍然可用，但没有独立进程负责停机后的升级。

运行设置、账号、角色、Self、记忆和文件都继续使用原数据目录。启动器运行期间不允许再用另一个 `npm start` 打开相同数据目录。macOS 的 `scripts/robots.mjs` 及原有双击入口可在私有 `deployment.json` 中设置 `managedUpdates: true`，让启动器保持原生 QQ 检查并管理新的 supervisor。必须先正常停止原桥接，再改变启动方式。

自定义 `--config` 路径暂不支持，应先将配置纳入指定数据目录。现有 systemd/launchd 等服务应改为启动 `npm run managed`，不要让旧启动器同时自动拉起桥接。

Docker 镜像也使用这个独立启动器。应用的新版本和依赖放在数据卷中，不修改镜像层，也不挂载 Docker socket。构建时提供 `--build-arg SOURCE_COMMIT=<完整提交 SHA>` 才能识别安装提交；提交未知时保留手动升级入口。新版本修改 Dockerfile、要求更高 Node.js 或不同升级协议时，必须重建镜像。启动更高版本的镜像时会优先使用镜像自带版本。

## 升级过程

1. 重新查询官方稳定发布，确认目标没有变化。固定从官方 Git 仓库克隆，在独立目录检出标签对应的完整提交，并确认当前提交是目标提交的祖先。
2. 检查项目、版本、升级协议和 Node.js 要求。用 `npm ci --ignore-scripts --omit=dev` 安装锁定依赖；本地修改、分叉历史和无法识别的安装会拒绝自动升级。
3. 停止新的管理修改和新回合，记录当时全局暂停及已连接的 QQ 连接。等待已经开始的回合、工具及投递收尾，期间继续保存新来信为待处理；完成后才全局暂停、关闭桥接，并确认进程退出和数据锁释放。
4. 备份整个数据目录，排除升级器自己的版本、备份和日志目录及进程锁；检查 SQLite 完整性。关键配置、凭据和 SQLite 文件的链接、硬链接、特殊文件、活动进程或空间不足会中止升级。普通符号链接仅保存链接本身，不跟随外部目标；外部目标不包含在备份中。配置、凭据、文件和模型 home 均在备份中，数据目录之外的 QQ/DSH 登录和系统配置仍需另行保管。
5. 用相同端口启动新版，保持全局暂停并锁住管理修改。恢复原先已连接的 QQ，原先允许运行时检查未暂停角色的 AI 后端。
6. 检查通过后保存当前版本指针，再恢复升级前的全局参与状态。角色及会话的暂停设置不变。管理台短暂断开期间自动等待重连，完成后点击「刷新管理台」。

下载和依赖安装阶段角色仍能正常工作；停机前显示“等待当前回合完成后停止运行”。已开始的回合沿用原有时限和权限，不因升级被主动取消。等待覆盖普通聊天、空闲活动、受保护工作和已发起的投递；超时返回 `UPDATE_DRAIN_TIMEOUT`，不切换代码、不强制结束回合，原服务保留在禁止新回合的维护状态。检查后可用本机 `restart` 重试等待，或明确执行 `stop` 中断工作。

已完成且仍兼容的会话保留引用、容量及已提供消息水位，重启后继续使用；身份、模型或工具契约变化仍可能要求重建。旧版升级器尚无等待能力，首次更新时按 [AI 更新手册](AI-UPDATE.md) 等待活跃回合结束，再安排切换。显式停止、撤权、回合本身超时和进程崩溃仍按取消/恢复规则处理，不承诺保留尚未完成的模型生成。

## 失败与中断恢复

- 下载或安装前置检查失败：当前服务继续运行，页面显示失败原因。等待回合完成期间失败：保留原服务及维护状态，不自动切换或恢复新回合。
- 新版启动或健康检查失败：确认候选进程退出后，保存失败数据，恢复旧代码和升级前备份，**保持全局暂停**。核对后手动恢复。失败期间接收到的记录保留在失败数据目录，不会静默删除，也不会自动合并进旧发送账本。
- 已经开始恢复发言后出错：停止自动回退，尽可能重新暂停。页面显示「需要检查恢复状态」，保留新版本数据，避免旧备份覆盖已产生的发送记录。
- 升级期间掉电或启动器被强制结束：默认拒绝继续启动。确认没有其他启动器或桥接仍在使用数据目录后执行：

```sh
npm run managed -- --data /path/to/data --live --recover
```

`--recover` 只回收已确认 PID 不存在的残留锁，不会终止其他进程。尚未进入恢复发言阶段时，使用完整的升级前备份恢复旧版；已进入该阶段时保留新版及现有账本。两种恢复都保持暂停，并忽略 `--resume`。若 PID 被其他进程复用或恢复失败，应检查现场后人工处理，不能直接删除锁来强行启动。

版本、事务、日志和备份位于 `<数据目录>/updates-runtime/`：`current.json` 记录正在使用的代码，`transaction.json` 记录升级阶段，`manager.log` 保存子进程日志，`backup-*` 是升级前备份，`failed-*` / `interrupted-*` 是失败现场。它们可能包含凭据和聊天，按私密数据保管。不会自动清理备份，磁盘不足时会拒绝新升级；确认不再需要回退后由管理员清理旧备份。
