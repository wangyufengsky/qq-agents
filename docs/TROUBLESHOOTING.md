# 故障排查

按症状查找。每节列出管理台显示的提示、对应的错误码、原因和处理方法。错误码与源码一致，可在管理台「最近错误」里按错误码筛选。

## 先看哪里

- **角色卡片**：「角色」页的设置里，“当前无法发言：…”列出所有挡住该角色的开关；首页卡片把同样的原因放在名字下面的一行“暂不发言：…”，太长时省略，鼠标停留可以看到全部。显示“各道开关已就绪”时，只剩下按会话判断的条件（白名单、会话暂停、会话静默）。
- **QQ 账号连接卡片**（「连接」页）：是否已连接、最近错误、自动重连状态和上次断线时间段。
- **AI 后端卡片**（「连接」页）：后端状态、最近检测时间和自动恢复次数，见 [后端连接状态与恢复](BACKEND-RECOVERY.md)。
- **最近错误**（概览底部）：本次启动以来的错误码，同类合并计数。

## 机器人不说话

角色发言前要通过下表中的每一道开关。前几行在角色卡片上直接显示；带“会话”标记的几行只针对具体群聊或私聊，不显示在角色卡片上。

| 错误码                          | 管理台显示     | 原因                                                                               | 处理                                                                                                                                                       |
| ------------------------------- | -------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `GLOBAL_PAUSED`                 | 全局暂停       | 全局暂停打开。**每次启动都会自动打开全局暂停。**                                   | 确认连接和后端正常后，在管理台解除全局暂停；或用 `npm start -- --live --resume`、`node scripts/robots.mjs start --resume` 在连接和后端检查通过后自动解除。 |

| `BACKEND_UNAVAILABLE`           | AI 后端不可用  | 该角色的 AI 后端正在恢复连接（手动或自动“恢复连接”进行中），期间不启动新回合。     | 通常在恢复结束后自动消失。持续存在或恢复失败时，到「连接」页查看状态，执行“检测连接”或“恢复连接”，见 [后端连接状态与恢复](BACKEND-RECOVERY.md)。           |
| `RECONFIGURING`                 | 配置正在生效   | 刚保存的配置正在应用到该角色。                                                     | 稍等片刻再看；不需要操作。                                                                                                                                 |
| `RUNTIME_CLOSING`               | 管理器正在关闭 | 进程正在停止。                                                                     | 等停止完成后重新启动。                                                                                                                                     |
| `NOT_ALLOWED`（会话）           | —              | 该群号或私聊对象不在角色的白名单中。白名单之外的消息不会被接收或回复。             | 在角色配置中把群号加入群白名单，或把 QQ 号加入私聊白名单。                                                                                                 |
| `CONVERSATION_PAUSED`（会话）   | —              | 管理员暂停了该角色在这个会话里的参与，其他会话不受影响。                           | 在「经历与日记」页的「来源」里选这个会话（如 `group:<群号>`），或展开页底的「会话状态」，解除该会话暂停。                                                  |
| `CONVERSATION_SILENCED`（会话） | —              | 角色自己选择在这个会话安静一段时间（工具 `qq_set_silence`），到期自动结束。        | 等静默到期；需要立即恢复时，在「经历与日记」页的「来源」里选这个会话，或在「会话状态」里对它执行“解除暂停 / 静默”（暂停或恢复会话都会清除静默）。          |

**所有开关都已放开，但角色仍不回复**，可能是以下正常行为：

- 唤醒条件没有满足。默认只在被 @、被叫名字（含别名）和私聊时唤醒，其他群消息按参与率（默认 5%）偶尔参与；问句唤醒默认关闭；开启后，只 @ 别人或引用别人消息的问句不会唤醒。可在角色配置中调整唤醒方式和参与率。
- 角色在被唤醒后自己决定不发言；普通的模型文本不会自动投递，只有调用发送工具才会发到 QQ。
- 连续发送达到 `maxConsecutiveSends` 上限，需要新的人类输入后才会继续；已配置同伴的私聊可在冷却后收到并完整读到新消息时恢复有限批次。重读、重建会话和单纯等待不会恢复，见 [连续聊天与联网策略](CHAT-NETWORK-POLICY.md)。
- 回合失败或超时（`BACKEND_TURN_FAILED`、`BACKEND_TURN_TIMEOUT`）。查看「最近错误」，恢复规则见 [回合失败与会话恢复](turn-recovery.md)。

## 连接断开 / 自动重连停止

管理员在本进程中**手动连接成功过**的 QQ 账号连接，接收通道意外断开（`CONNECTION_LOST`、`ONEBOT_WS_ERROR`），连接看似还在、但 90 秒内连 WebSocket ping 的回应都没有（`ONEBOT_HEARTBEAT_TIMEOUT`，常见于 NAT 超时、机器睡眠后恢复或 NapCat 卡死），或者 NapCat 还在、但报告 QQ 已离线（`QQ_OFFLINE`，见下文）后，会按指数退避自动重连：默认首次约 2 秒后、之后逐次翻倍，最长间隔 5 分钟，最多 8 次。连接卡片会显示“自动重连等待中：已尝试 n/8 次”或“正在进行第 n 次自动重连”。

- 自动重连只恢复接收，**不重发**任何消息，也**不补录**断线期间的群消息；卡片会显示“上次断线 … 期间的消息未补录”。
- 重新启动进程后不会自动连接；需要再次手动连接，或带 `--live --resume` 启动（`npm start` 和 Docker 都可以），或使用 `scripts/robots.mjs start` 由启动器连接。
- 网关发来一条无法解析的消息时，只丢弃这一条并在卡片上显示 `INVALID_ONEBOT_EVENT`，接收通道保持连接；收到另一个 QQ 号的消息则以 `QQ_ACCOUNT_MISMATCH` 断开且不重连。
- 运行模式不是 `live` 或配置正在保存时，暂不重连。
- QQ 被其他设备顶下线、登录过期或触发风控时，NapCat 进程和网络连接往往还在。网关发来 `bot_offline` 通知，或心跳里明确写着 `status.online=false` 时，桥接立即断开这条连接并显示 `QQ_OFFLINE`，角色卡片随之显示“QQ 未连接”，不会再对着一个已离线的账号发送。之后的自动重连只查询 `get_login_info` 和 `get_status`，**不会**替 QQ 重新登录，也不会重启 NapCat，因此不会因反复登录刺激风控；需要有人在 NapCat 重新登录（通常要扫码），登录后下一次重试就会接上。卡片显示“QQ 账号已离线 … 需要在 NapCat 重新登录”；如果重试次数已用完，登录后手动点“连接 QQ”。心跳里不带 `online` 字段的网关不受影响。
- 想在 QQ 里收到掉线提醒，可以给可能掉线的角色开启“QQ 掉线时请其他角色告诉主人”（`behavior.outageNotice`，见 [QQ 掉线通知](CONFIGURATION.md#qq-掉线通知)），由同一实例里另一个在线的角色私聊告诉它的主人。没收到时看诊断：`OUTAGE_NOTICE_NO_SENDER` 表示没有可以代发的角色（只有一个角色、其他角色的 QQ 也掉了或都暂停了、主人不在它们的私聊白名单里），`OUTAGE_NOTICE_NO_OWNER` 表示掉线的角色没有填写主人 QQ；被暂停、静默或发送限额拦下时同样只记诊断、不重试。冷却期（默认 30 分钟）内同一连接的同一种提示不会重复。

| 卡片提示 / 错误码                                         | 原因                                                                                                                               | 处理                                                                                                                               |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 自动重连已停止（多次失败）/ `QQ_AUTO_RECONNECT_EXHAUSTED` | 重试次数用完仍未连上。                                                                                                             | 检查 NapCat 是否在运行、QQ 是否仍在线、端口是否变化；修复后手动连接，计数随之重置。                                                |
| 自动重连已停止：QQ 账号仍未登录                           | 掉线原因或最近一次重试的结果是 `QQ_OFFLINE`：NapCat 能连上，但 QQ 没有登录。                                                       | 在 NapCat 重新登录这个 QQ 号，然后手动连接。                                                                                       |
| 自动重连已停止（登录账号不匹配）/ `QQ_ACCOUNT_MISMATCH`   | NapCat 当前登录的 QQ 号与连接配置的 `accountId` 不一致（换号登录，或地址指向了另一个实例）。这类错误不会靠重试恢复，因此立即停止。 | 让 NapCat 重新登录正确的 QQ 号，或核对 `httpUrl`/`wsUrl` 指向的实例；确认无误后手动连接。不要为了连上而把 `accountId` 改成别的号。 |
| 自动重连已关闭或连接已停用                                | 该连接关闭了自动重连，或已被停用。                                                                                                 | 需要时手动连接；或在连接配置中重新开启自动重连。                                                                                   |

`ONEBOT_TOKEN_ENV_MISSING`、`CONNECTION_DISABLED` 和 `ISOLATED_MODE` 同样会让自动重连立即停止。连接的 `recovery` 设置项：`autoReconnect`（默认开启）、`maxAttempts`（1–20，默认 8）、`initialDelayMs`（1000–60000，默认 2000）、`maxDelayMs`（5000–600000，默认 300000）、`heartbeatTimeoutMs`（0 或 15000–600000，不填时为 90000；设为 0 关闭心跳检测）。

## 启动报 `DATA_DIRECTORY_LOCKED`

管理台运行时在数据目录里持有 `process.lock`，正常退出时删除。进程被强制结束（`kill -9`、任务管理器结束任务、断电、Docker 超出停止宽限期或内存不足被杀）时锁会留下来，下次启动报 `DATA_DIRECTORY_LOCKED`。程序不会自动回收旧锁，因为两个进程同时写同一个数据库会损坏数据。

1. 先停止所有自动拉起（`robots.mjs`、systemd、`docker compose` 的 `restart`）。
2. 查看锁里记录的 PID 和启动时间，确认该进程已不存在，也没有其他进程或容器在使用同一个数据目录。
3. 删除 `process.lock`，再启动一个实例。

Windows 和 Docker 的具体命令分别见 [Windows](WINDOWS.md) 和 [Docker 部署：停止与残留锁](DOCKER.md#停止与残留锁)。

## 群图片收到但读取失败

`IMAGE_DOWNLOAD_HTTP_ERROR` 表示图片服务器拒绝了下载或返回了不支持的响应，不能据此认定网络超时或签名已过期；`IMAGE_DOWNLOAD_TIMEOUT` 才表示下载期限已到。图片链接返回错误时，NapCat 可能仍能取得原图。

对当前账号实时收到、仍在允许会话内的图片，程序会在链接下载失败或缺失后尝试一次 NapCat 原图流接口。回退只使用消息中已经观察到的图片文件标识，不读取网关返回的本机路径，也不接受模型指定的下载目标。开始回退和写入缓存前，都会检查同账号、同会话下关联的真实撤回通知；原消息的状态字段不会随撤回改变。原图仍受大小上限、取消信号、并发限制和完整传输回执校验；QQ 提供的压缩图大小可能与原图不同，因此原图流以实际字节数和结束回执核对。普通文件附件仍要求声明大小与实际大小一致。成功读取后按角色、来源消息和图片序号缓存，再次读取无需重新下载。

图片文件标识支持 32 位十六进制名称和带花括号的 UUID 名称；允许尝试不代表网关一定保存着该原图，仍可能返回文件不存在。QQ 也可能把 GIF 标为 `.jpg`，因此下载上限不能只按后缀判断：来源最多 20 MiB，实际内容为静态图片时仍执行 8 MiB 上限。

如果原图流也失败，角色仍不能描述图片内容；检查 QQ 客户端是否还能打开原图，必要时重新上传。管理台保留原图流错误码，并在“原因”中保留之前的链接下载错误码；签名链接、凭据和本机路径不会进入错误提示。

## 发送结果未知

**症状：** 概览出现“待核对发送 · n”。

**原因：** 发送请求已经交给 NapCat，但没能确认结果——例如网络超时，或进程在发送途中退出（重启时仍处于“发送中”的记录会被标为未知）。消息可能已经发到 QQ，也可能没有。为避免重复发言，**结果未知的发送永远不会自动重发**。

NapCat 等不到 QQ 的发送确认时（日志里是 `Timeout: NTEvent ... sendMsg`，常见于 QQ 在发送途中短暂离线），也按“结果未知”记录，不再当作发送失败：QQ 恢复后这条消息往往仍会发出。之后 NapCat 回传的本账号消息如果出现在同一会话、十分钟内、文字与这次发送完全一致，并且只对得上一条未知发送，程序就把它标为“已发出”并记下 QQ 的消息 ID（记录里写 `reconciledBy: gateway-echo`），不会重发。只有图片、文字对不上或同时有多条相同文字的未知发送时，仍留给管理员核对。

**处理：**

1. 在「待核对发送」中查看该条的会话和内容预览。
2. 到 QQ 中打开对应的群聊或私聊，确认消息是否出现。
3. 标记为“已发出”或“未发出”。两种结论都只更新记录，不会重发同一请求；需要补发时由角色在之后的回合中自行决定。

同一条记录已被标记后再次标记会返回 `DELIVERY_ALREADY_SETTLED`，刷新页面即可。已预留但尚未提交给 NapCat 就被取消的发送记为失败（`CANCELLED_BEFORE_SEND`），不会出现在这里。

## 配置保存冲突

**症状：** 保存时提示“配置已变化，请刷新页面后重新核对修改。”（`CONFIG_CONFLICT`）

**原因：** 管理台保存时会带上读取配置时的版本号。以下情况会让保存被拒绝，以免覆盖别人的改动：

- 在另一个浏览器标签页、`scripts/robots.mjs` 或其他管理操作中，配置已经被修改并保存（例如解除了暂停）；
- 上一次保存还在生效中，或该连接正在重连、该角色正在重新配置、后端正在恢复。

**处理：** 刷新页面，确认当前配置后重新做一遍修改并保存。不要在进程运行时手动编辑 `config.json`。

相关错误：

| 错误码                                    | 含义                                                                                                       |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `CONFIG_SAVE_FAILED`                      | 写盘失败，当前配置和回合保持原状。查看「最近错误」中的磁盘诊断。                                           |
| `RESTART_WITH_LIVE_FLAG_REQUIRED`         | 进程不是以 `--live` 启动的，不能把运行模式保存为 `live`。                                                  |
| `LIVE_CONFIG_REQUIRES_EXPLICIT_LIVE_FLAG` | 启动时报错：配置已是 `live`，但启动命令没有 `--live`。改用 `npm start -- --live` 或 `scripts/robots.mjs`。 |
