# 第一轮可靠性修复：停机、配置提交与错误诊断

本轮覆盖进程退出、在途任务收敛、配置版本与提交、错误分类和管理台诊断。回归使用临时数据目录、合成后端和本机网关；不代表生产部署、真实 QQ 出站或真实模型验收。

## 停机契约

- 首次 SIGINT / SIGTERM 停止接收业务请求和定时唤醒，同步撤销工具能力并取消回合。HTTP 与 Runtime 协作收敛；数据库保持可用，直到完整请求、回合、owner context、后台任务和发送队列结束。
- 已发出的投递继续记录网关回执，排队但尚未发出的请求被撤销门禁拒绝。成功回执不会因取消或后续审计异常降级；失败和未知结果不自动重放。
- 关闭使用共享 Promise。一个资源关闭失败仍尝试其他资源，并记录脱敏诊断，进程退出码为 1。握手中的连接会被取消，旧 socket 的晚到事件不会改变新连接。
- 默认总宽限为 30 秒，可用 `--shutdown-timeout-ms` 设置 1–120000 毫秒。总截止时间包含 HTTP、后端、队列及受管进程清理；资源自身的网络超时仍保留。此截止时间依赖事件循环，不能打断同步阻塞或失去响应的操作系统调用。
- 达到截止时间或收到第二次信号时，在同一同步退出边界将仍为 `pending` 的投递标为 `unknown`，关闭数据库、校验并释放本进程锁，再以 1 退出。若磁盘写入本身失败，持久记录可能仍为 `pending`；同样禁止自动重发。强制退出不能保证外部模型或 QQ 子进程都已结束，需要依据诊断检查实际进程。
- 嵌入使用者应等待 `Runtime.close()` 完整完成后再关闭 MemoryStore。进程层的强制退出依赖立即 `process.exit()`；不能把退出函数替换为继续运行的回调后仍声称安全关库。关闭完成后的会话、用量和图片回调被忽略。

进程锁通过独占创建产生，记录 PID、启动时间和随机所有权标记。释放时同时核对文件身份与标记，不删除被替换的锁。锁创建失败区分 `DATA_DIRECTORY_LOCKED` 和 `PROCESS_LOCK_CREATE_FAILED`。不会自动抢占、回收旧锁。SIGKILL、断电仍可能留下锁；恢复时必须先停止自动拉起，核对记录的 PID、进程启动时间、实际数据目录及受管子进程，确认没有旧实例使用该目录后才由管理员移走残留锁，再启动一个实例。不能只凭 PID 查询失败或锁文件较旧就删除。

## 配置提交与客户端兼容

完整配置更新遵循校验、检查影响、原子写入、同步权限失效、异步运行态更新的顺序。临时文件写入或 rename 失败时返回 `CONFIG_SAVE_FAILED`，当前配置、版本、连接和回合保持原状。损坏的已有配置返回 `CONFIG_INVALID_JSON` 或 `CONFIG_SCHEMA_INVALID`，不会用示例覆盖。

`GET /api/config` 的 `revision` 现在是校验后配置内容的 SHA-256 字符串，跨重启保持稳定。客户端必须把它当作不透明值原样提交，不再自增，也不能继续提交旧数字版本。配置内容发生变化后，旧页面的保存返回 HTTP 409 / `CONFIG_CONFLICT`，需刷新并重新核对修改。配置文件仍为 version 1，没有新增数据库 schema 或配置包裹层。同一内容的重复保存可以保留相同 revision；它表示内容版本，不是提交次数。此机制用于单实例内的管理请求，不为运行中直接改文件或多个独立进程共写配置提供文件锁。

落盘成功后，若后端清理或派生状态同步失败，响应明确保留 `saved: true` 并附 `warnings: ["CONFIG_RECONFIGURE_FAILED"]`，管理台提示已保存但运行态更新未完成。不要重复提交同一修改来试图回滚；先按最近错误处理故障，再恢复服务。全量变更仍需手动重新连接 QQ；仅参与率和主体调度参数修改继续使用现有轻量路径。

## 诊断与排障

管理 HTTP 错误保留稳定 `error` 字段，增加 `requestId`、`retryable`，响应头包含 `x-request-id`。输入错误为 400，认证与权限为 401/403，配置冲突为 409，请求体过大为 413，预算耗尽为 429，内部错误为 500，临时不可用为 503。`retryable` 仅描述错误类别，不授权自动重放有副作用的操作。模型工具继续沿用既有安全错误结果，并在 HTTP 工具入口记录相同请求的诊断。

默认诊断为 stderr JSON Lines。仅输出受审查的错误码、组件、时间、关联 ID、计数、安全原因及可用的耗时；角色与会话组合仅以摘要参与聚合。不会把原始上游 message、cause、stack、请求参数、正文、token、路径或环境变量序列化。新增公开错误码需要加入 `src/core/error-codes.mjs` 并审查其分类；未知错误映射为 `INTERNAL_ERROR`。

同组件、错误码及作用域的异常聚合计数，每类最多每 5 秒输出一次，所有诊断合计最多每分钟 100 行。管理台“概览 → 最近错误”保留本次启动的最近 50 类摘要，可按错误码、组件或关联 ID 筛选。重复事件被聚合时不保证每个关联 ID 都有独立日志行，界面保留该类最近一次 ID。日志写入失败不覆盖原业务错误。长期留存及轮转依赖部署层收集 stderr；进程内摘要不跨重启保存。

建议排障顺序：记录响应关联 ID → 查看管理台最近错误及安全原因 → 查部署日志的同类记录 → 修复磁盘、权限或后端状态 → 重新核对配置和回执。`unknown` 不是“未发送”，应先查网关/QQ 实际结果，不能换 requestId 自动补发。

## 回归范围

`npm run verify` 执行语法检查、全部 Node 测试、格式检查和隐私扫描。本轮重点覆盖：关闭重入；直接回合和 owner context；HTTP 在途回执与排队发送；关闭失败；握手取消；晚到回调；真实子进程正常信号、超时、第二次信号及锁竞争；配置保存失败、跨重启版本冲突、坏文件和提交后故障；HTTP 错误分类、脱敏、重复聚合及诊断输出失败。

部署仍需独立安排暂停、备份、启动与真实平台验收。回滚本轮代码不需要数据库迁移；保留配置文件，并刷新管理台使旧版本客户端重新取得其支持的 revision。不要把回滚当作重放未知投递的理由。
