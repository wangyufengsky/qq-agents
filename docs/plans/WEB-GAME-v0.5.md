# 多游戏网页框架契约 v0.5

状态：分阶段实施。P1a 已实现通用内核、服务端身份绑定原语和仅本机的非棋盘夹具，操作与实际边界见 [P1a 指南](../WEB-GAME-P1A.md)。[P1b 五子棋规则与界面](../WEB-GAME-P1B.md)已接入同一内核；[P2](../WEB-GAME-P2.md)已实现 QQ 来源适配、隔离 AI worker 和默认关闭的独立入口，首个后端为 Codex；真实跨网完整对局仍需 P3 验收。五子棋仍是第一个产品试点；P0 继续作为独立访问实验。

## 与 v0.4 的关系

本文件是后续实现的入口。继承 [v0.4](WEB-GAME-v0.4.md) 的身份确权、邀请凭据隔离、精确 Host/Origin 与 HTTPS 校验、事务幂等、可靠投递、租约、远端执行对账、预算及公网隔离要求。下列约定以 v0.5 为准；没有列出的安全与恢复约束继续适用。

| 原约定                                | v0.5 约定                                                                                      |
| ------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 核心产品围绕五子棋描述                | 产品为可扩展网页游戏能力，五子棋实现首个游戏模块                                               |
| `board`、坐标、黑白棋子、两名玩家     | 通用层只持有模块引用、参与者与私有游戏状态；具体结构由模块定义                                 |
| `game_act(..., move)`                 | 统一提交 `action={type,payload}`，规则模块校验游戏动作                                         |
| HTTP 动作正文中的 `type,payload`      | 收入 `action` 对象；幂等主体统一称 principalId，即 v0.4 的已认证 actorId，不取自正文           |
| AI 任务键 `(roomId,revision,agentId)` | 任务键 `(roomId,decisionId,participantId)`；绑定来源版本与真实 agentId，只对待行动的 AI 建任务 |
| 房间共用一个概念游戏上下文            | AI 上下文按房间、参与者和真实 agentId 隔离，不能复用另一参与者的隐藏信息                       |
| P1 直接实现五子棋与房间               | P1 先交付通用内核和模块契约，再接五子棋及非棋盘契约夹具                                        |

P0 的固定 15×15 棋盘、`x/y` 参数、225 版本上限、单个测试 Cookie 与黑白交替逻辑仅属于实验。P1 使用独立的新数据结构，不把 P0 测试身份自动升级为 QQ 身份，不自动导入 P0 测试局。[P0 操作说明](../WEB-GAME-P0.md)仍只描述已经实现的实验程序。

## 首版能力与扩展边界

首版内核的能力标识为 `turn-sequential-v1`：固定参与者、事件驱动、任一时刻至多一名参与者需要行动。人数范围由模块声明并受平台上限限制；平台参与者上限暂定 8，五子棋模块固定 2。人类、AI 都是参与者，在线连接是独立对象。

支持公开行动进度、按参与者隐藏内容、受控随机性，以及由模块定义个人或共同结果。这里的“隐藏”保护值，例如手牌、选择和答案；首版授权参与者可以看到全局 revision、行动者和行动发生的事实。若游戏连“某人是否已行动”都需要保密，须使用未来的独立视图版本协议，首版拒绝注册该能力。

同时提交、竞速抢答、实时物理/动作同步、局中增减参与者或换座不属于 `turn-sequential-v1`。这些能力需要新的并发、信息可见性和调度契约；不得借轮询或频繁模型调用冒充支持。多人顺序行动、合作结果可复用当前抽象，是否作为可用产品开放须逐游戏验收。

## 职责与依赖方向

| 层次             | 负责                                                                      | 不得承担                                                   |
| ---------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 通用房间内核     | 身份绑定、参与者、生命周期、版本、事务、回执、事件、限额、执行门禁        | 棋盘尺寸、黑白轮次、出牌规则、猜谜答案、游戏胜负算法       |
| 游戏规则模块     | 配置与动作 schema、初始状态、合法性、状态转换、下一行动者、结果、视图投影 | HTTP/Cookie、QQ 发送、模型调用、数据库、任意网络或文件读写 |
| 通用网页外壳     | 会话、连接状态、版本同步、待确认操作、重连与手机基础交互                  | 根据服务端私有状态猜测胜负或替服务端裁决                   |
| 游戏网页模块     | 展示参与者视图、采集该游戏的候选动作、交互说明                            | 持有权威完整状态、生成身份或租约凭据                       |
| AI 适配与 worker | 从裁剪视图生成任务、调用已授权后端、附加不可变执行上下文、统计预算与对账  | 自行改房间状态、绕过规则、从网页参数决定角色身份           |

依赖为 HTTP/网页外壳或框架适配器 → 通用内核 → 注册的规则模块。内核通过稳定接口调用模块，不使用 `if (gameType === "gomoku")` 等规则分支。五子棋界面可以专用；不要求所有游戏共用一个棋盘组件，也不引入通用场景编辑器或脚本引擎。

初期只注册随项目审阅、验证和发布的可信内置模块。注册不是安全沙箱；模块代码不能由模型、邀请链接或网页上传，不动态执行远程代码。第三方模块隔离与安装权限另立设计。

## 模块注册与版本

注册表按 `(gameType,moduleVersion)` 定位不可变发布模块。清单至少包含下列字段：

| 字段                 | 契约                                                                              |
| -------------------- | --------------------------------------------------------------------------------- |
| `gameType`           | 稳定小写标识，例如 `gomoku`；名称展示与标识分开                                   |
| `moduleVersion`      | 整包精确发布版本，任何发布内容变化都须新建版本，禁止同号替换                      |
| `moduleApiVersion`   | 初始为 `1`，宿主接口版本，不等于游戏规则版本                                      |
| `rulesVersion`       | 精确规则版本；规则、状态转换或随机算法语义变化必须新建版本，禁止同号替换          |
| `stateSchemaVersion` | 私有状态结构版本；不能只靠此字段判断旧规则是否兼容                                |
| `uiVersion`          | 对应视图协议和前端资源的精确版本                                                  |
| `moduleDigest`       | 发布内容摘要，覆盖清单、规则、schema 与前端资源；服务端校验，不接受客户端声明替代 |
| `capabilities`       | 行动模式、隐藏信息策略、随机性及结果类型；未知或宿主不支持的能力拒绝注册          |
| `participants`       | 人数范围、允许的主体种类和组成约束；最终名单由平台认证并冻结                      |
| `schemas`            | options、私有 state、按类型的 action payload、各类 view 及 outcome 的校验定义     |
| `limits`             | 模块声明的状态、视图、动作与随机材料上限，只能收紧平台上限                        |

房间创建时记录整份模块引用；客户端只选择已公开的游戏与 options，服务端选择允许的精确版本。只修界面也发布新 moduleVersion/uiVersion；只有规则与状态转换保持一致时才可保留 rulesVersion。既有房间不随最新版本自动切换。首版不提供局中迁移，须保留旧模块和资源至对应房间结束并过保留期；缺少精确版本时返回 `GAME_MODULE_UNAVAILABLE`，保留数据并阻断操作，不能用新规则猜读旧状态。

2026-11 优化补充：规则摘要只覆盖规则/schema 源码及实际规则依赖的精确版本，不包含无关锁文件与前端资源。界面独立发布 UI 版本，并明确兼容的规则版本；新建房仍使用新的 moduleVersion/uiVersion。旧房间只有在精确发布引用列入兼容清单、规则源码指纹与依赖版本均匹配时，才复用同一规则实现并加载兼容的新 UI；不改写房间、决策、执行记录中的原引用，不把任意未知摘要映射到最新模块。规则或 schema 变化必须保留旧实现或拒绝部署。此补充取代首版“只修 UI 也必须保留旧 UI 资源”的限制，旧状态的解释和动作校验边界保持不变。

## 房间、参与者和状态

房间持久记录以下逻辑对象，不要求它们必须放在同一张 SQL 表：

| 对象                           | 内容与所有权                                                                            |
| ------------------------------ | --------------------------------------------------------------------------------------- |
| `moduleRef`、`options`         | 固定模块版本及已校验的开局配置；开局后不可修改                                          |
| `participants`                 | 稳定 participantId、座位/阵营配置与确认状态；私有表关联人类主体或真实 agentId、授权来源 |
| `lifecycle`                    | waiting/active/paused/finished/expired，由通用内核拥有；游戏内部阶段保存在 state        |
| `revision`                     | 单调安全整数，不等于手数、回合数或棋盘容量                                              |
| `state`                        | 模块校验的权威私有 JSON，包括隐藏信息；只在服务端规则边界可见                           |
| `decision`                     | 平台生成的 decisionId、participantId、sourceRevision；没有待行动者时为 null             |
| `outcome`                      | 模块给出的游戏结果或平台给出的结束原因；不能混淆自然结束、放弃和过期                    |
| `eventSeq`、回执、outbox、预算 | 通用内核持有，规则模块不能自行重置或删除                                                |

房主是管理权限，不天然拥有替其他参与者行动的权限。principal → participantId 的映射由 Cookie 或已认证内部上下文派生，`seatId`、昵称、actorId 或网页提交的 QQ 号均不是凭据。waiting 期间按绑定流程确认名单；开局冻结名单与座位，重新加入只恢复原有身份。首版同一真实 agentId 在同一房间最多占一个参与者位置。

AI 上下文使用 `(roomId,participantId,agentId,moduleRef)` 隔离。agentId 仍是稳定记忆身份，不创建替身角色；共享一个 backendId 也不能共享另一参与者的模型会话。每个 AI 都须具有独立有效的来源授权，创建者不能借邀请给其他角色扩大权限。

## 规则模块调用契约

以下名称是规则模块接口；P1a 的具体调用封装和宿主入口见 [实现指南](../WEB-GAME-P1A.md)，不表示模型工具已经开放。调用使用普通可校验 JSON，输入只读；平台保留输入副本，拒绝非法返回值和超出资源限制的结果。

| 接口          | 输入                                                   | 返回与约束                                                                                                        |
| ------------- | ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| `create`      | 已校验 options、冻结的 participants、平台 context      | 初始 state；只在开局事务调用一次                                                                                  |
| `applyAction` | state、已认证 participantId、`{type,payload}`、context | 新 state 或稳定拒绝码；负责阶段、行动者与规则合法性，不能改原对象                                                 |
| `nextActor`   | state、participants                                    | 一个 participantId 或 null；返回未知参与者或多个参与者是模块契约错误                                              |
| `outcome`     | state、participants                                    | null 或 `{kind,winners,reasonCode,details}`；winners 为有效参与者集合，可为空或多人，details 必须经投影后才可外发 |
| `projectView` | state、viewer、已校验的模块配置                        | 面向该参与者的 view 和动作 schema/提示；不返回权威 state                                                          |

viewer 由平台构造，至少包含 `kind=participant` 和已认证 participantId；投影所需的冻结名单、展示座位与 options 由已校验模块配置提供，不能从网页自由指定。房主管理权限不产生全知视图；未来 spectator 使用另一种 viewer，首版拒绝。规则模块只接触规则所需的稳定参与者标识与座位，不取得真实 QQ 标识、授权凭据或模型会话引用。

游戏 outcome 的 kind 为 `win`、`draw` 或 `loss`。win 的 winners 必须是非空有效参与者集合，允许全员共同获胜；draw/loss 的 winners 为空，分别表示和局与共同失败。reasonCode 由模块注册，details 遵守该版本的 outcome schema。平台关闭或过期使用独立的结束原因，不伪造游戏 outcome；对外结果只从 projectView 取得，不能直接附加内部 details。

`create`/`applyAction` 的 context 只包含平台冻结的逻辑时间与有界随机材料等规则输入，不包含凭据、QQ 配置、聊天数据库或后端句柄。模块不得自行取系统时钟、调用非确定随机源或执行 I/O。同一版本、同一输入与同一 context 必须给出相同结果。平台将成功转换的 context 与内部动作记录一起原子保存；重放使用原 context，幂等重试不重新抽随机数。随机材料和内部记录不进入玩家视图、模型提示或公开日志。

首版 active 房间必须有下一行动者或已产生游戏结果。`nextActor` 为 null 且 `outcome` 为 null 应作为 `GAME_MODULE_INVALID_RESULT` 拒绝提交；首版不支持隐式后台规则推进。游戏结束必须返回 outcome，且下一行动者为 null。未来定时游戏须新增可持久化、幂等的系统事件入口，不能在 view 或轮询中推进规则。

平台先校验 manifest/schema、状态和主体，再在同一事务内调用转换及检查新状态、下一行动者、结果和必要投影。任一步抛错或输出不合法，整次事务回滚，不能留下已变更状态但没有回执的局面。模块错误映射为稳定错误码，不能返回原始 state、输入或异常堆栈。可信模块仍须进行有界工作与故障测试；首版不把 JavaScript 调用包装成 Promise 超时当作 CPU 隔离保证。

## 可见性与信息流

HTTP view、SSR、网页初始数据、AI prompt、动作提示及后续事件都从对应 viewer 的投影派生。不能先把完整 state 送到客户端再隐藏控件；不能把完整 state 给模型后用提示词要求它保密。身份在投影前校验，未认证入口只显示最小房间状态。

首版对授权参与者公开的是游戏类型与版本、名单中的展示身份、lifecycle、revision、当前行动者及结束状态。隐藏字段、选项提示、错误原因、日志和结果回执均须检查是否可推断别人的私有值。依赖隐藏值的拒绝使用不含该值的统一规则错误；首版不承诺消除计算耗时等所有侧信道。

增量事件只发送经授权的通用通知，例如 `view_changed`、`room_paused`，携带 eventSeq/revision，随后读取最新投影；不透传内部动作正文、随机材料或原始状态差异。过旧游标要求重取视图。动作回执只返回该主体有权查询的确认信息；服务端私有审计记录与网页回执是不同数据。

观战属于 P4，必须使用单独的 spectator 投影与权限。终局不会自动公开所有隐藏信息，是否揭示由该规则版本的投影决定。回原 QQ 会话的结束摘要使用审阅过的公共结果摘要，不直接转发某个参与者的私有 view 或模型内部上下文。

## 动作封装、事务和生命周期

所有写动作使用同一封装，以下为五子棋的一个示例：

```json
{
  "actionId": "00000000-0000-4000-8000-000000000001",
  "expectedRevision": 7,
  "action": {
    "type": "game.place",
    "payload": { "x": 7, "y": 7 }
  }
}
```

`room.*` 保留给平台控制动作，`game.*` 由模块注册，避免游戏伪装房间管理命令。未注册类型、未知字段、不合 schema 的 payload 均拒绝；游戏只接收自己的动作。平台统一处理 `room.start`、`room.pause`、`room.resume`、`room.close` 与到期处理；五子棋的 `game.resign` 属于规则动作，不能用管理员 close 冒充对手获胜。

处理顺序固定为：

1. 认证并确认当前主体仍有读写该房间的权限，取得 participantId 或房主管理身份。
2. 在事务内检查 `(roomId,principalId,actionId)` 原回执；相同请求返回原确认信息，不重新执行模块。同键不同规范化请求返回 `IDEMPOTENCY_CONFLICT`。principalId 是平台内部主体标识，不接受请求正文提供。
3. 对新动作检查生命周期、expectedRevision、模块版本、权限和 AI 执行上下文。请求摘要覆盖动作类型、payload 与 expectedRevision。
4. 执行平台控制转换或游戏转换，校验全部输出；冻结名单、规则配置等平台字段不能被游戏返回值覆盖。
5. 接受的新动作递增 revision 一次，并原子写入 state、lifecycle/outcome、回执、通知、下一决策及 outbox。提交成功后才响应、投递通知或安排模型。

拒绝动作不推进 revision，幂等重放不推进 revision；回合数等游戏计数单独放在 state。开局、确认名单的持久变更、暂停、恢复、结束、过期同样使旧版本失效。在线状态、心跳、轮询、任务进度和短评只影响 eventSeq，不制造新的 AI 决策。

waiting → active 需要已确认的名单和明确开局操作；paused 保留 state，禁止游戏写入；resume 重新检查参与资格、期限与门禁；finished 保留终局视图和旧成功回执；expired 拒绝新动作，按保留策略清理。过期、撤销权限及数据删除继续遵守 v0.4 的鉴权和回执边界，不复用 roomId。默认空房、活动、暂停和终局期限继承 v0.4，模块不能靠轮询续期或放宽平台保留上限。

平台初始资源上限约定：动作封装 16 KiB，私有 state 256 KiB，单个 view 64 KiB，单次随机材料 64 字节；每局最多接受 10000 个动作，超过后阻断新动作并允许受控结束。均按实际 UTF-8/字节长度校验，模块 limits 只能更小。这些是 P1 目标值，未改变 P0 已有的限制；房间数量与模型额度另受部署配置约束。

## 人类接口与 AI 工具

| 接口/工具                                           | 契约                                                                                      |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `POST /rooms/:id/join`                              | 延续显式兑换与 QQ 绑定，不接受 gameType、座位主体或规则版本切换                           |
| `GET /rooms/:id/view`                               | 返回通用 envelope 与当前 viewer 的模块 view、动作说明；无 state 原文                      |
| `POST /rooms/:id/actions`                           | 接受统一动作封装；主体从认证上下文取得                                                    |
| `GET /rooms/:id/actions/:actionId`                  | 仅返回当前主体可查询的原回执；成功后可再请求最新 view                                     |
| `GET /rooms/:id/events?after=…`                     | 有界授权通知；不触发模型、不透传私有事件                                                  |
| `game_create(gameType,options,invitees,requestId)`  | 已注册游戏、schema 校验配置、经框架确认的参与对象；不接受任意模块 URL，模型不取得私密邀请 |
| `game_view(roomId)`                                 | 通过本回合真实 agentId 绑定到该 AI 参与者，取得裁剪视图和可执行动作                       |
| `game_act(roomId,expectedRevision,actionId,action)` | 同一动作封装；适配器附加不可变 executionContext，模型不能填写或升级租约                   |
| `game_close(roomId,requestId)`                      | 映射为有权限的 `room.close`，明确这是结束房间而非游戏获胜                                 |

game_create 的幂等、邀请发送账本及敏感凭据处理继承 v0.4；game_close 的内部幂等映射须持久保存首次构造的完整动作，包括 actionId 与当时读取的 expectedRevision。重试不能另造操作或更新版本绕过冲突；冲突须重新观察后明确发起新请求。P2 当前实现范围、来源票据参数、可用执行范围和启用方式见 [P2 指南](../WEB-GAME-P2.md)；普通聊天只开放创建和关闭，view/act 留在独立游戏回合。

浏览器共享会话、请求、待确认队列和同步协议。游戏 UI 只产生候选动作，提交前由外壳绑定当前 revision；版本变化使旧候选动作失效。待确认操作按房间与当前主体/会话隔离存储；退出或撤销后不得在另一身份下自动重放。模糊结果沿用原 actionId 对账，规则模块和 UI 都不能自行换编号自动补交。

## AI 决策、租约和预算

规则模块只返回“下一行动者”，平台在成功状态转换后生成并持久化新的 decisionId。`jobKey=(roomId,decisionId,participantId)`，记录真实 agentId、moduleRef 与 sourceRevision。仅当房间 active、待行动者为 AI 且框架门禁允许时，worker 才可运行；人类回合、页面刷新和在线通知不调用模型。

同一未解决决策的消息重投或人工重试沿用 jobKey；非法动作没有提交状态转换时仍是原决策。成功游戏动作后的下一行动机会，即使仍轮到同一参与者，也生成新 decisionId。暂停、结束、过期或撤销使旧决策不可提交；恢复后建立新 decisionId。不能把它作为绕过旧模型运行对账的办法：后端尚未证明旧运行终止时，替代执行仍保持 blocked/outcome_unknown。

`executionContext={jobKey,runId,fencingToken}` 的不可变绑定、单调 fencing、租约/续租时限、失效处理与远端终态证明继承 v0.4。提交还必须匹配当前 decisionId、participantId、agentId、sourceRevision 和模块引用；租约验证、规则转换与落库位于同一事务。旧 worker 无法通过读取最新 view 为自己更换执行上下文。

决策 outbox 只带任务引用与必要版本元数据；worker 执行前重新认证并取 AI 自己的 view。模型能看到的规则说明、动作 schema 和参数提示也须符合该参与者的可见性，不允许游戏模块给模型附加任意工具权限。框架按现有后端契约提供真实角色、预算和取消控制；QQ 断线、全局/角色/来源会话暂停、静默和隔离模式继续优先。

每局、每角色及框架总预算共同生效。尝试前原子预留，服务商重试、后端恢复和非法动作修复均计入；未知用量保留预留，失败不能靠新建 decisionId 清空历史消耗。首版只接一个经过真实验收的后端，其余后端逐一适配，不把统一接口当作兼容性证明。

## 首个模块与扩展契约夹具

五子棋模块 `gameType=gomoku`：15×15、黑先、无禁手、连续五个及以上获胜、满盘无胜者和棋；首个产品预设一人一 AI。模块拥有棋盘、颜色分配、当前回合、落点校验及胜负算法，动作至少为 `game.place` 和 `game.resign`；网页模块拥有棋盘、坐标和局部放大。双方看到的棋局为公开信息，但仍经过统一 projectView。平台不得出现 15、225、黑白或五连等规则常量。

另定义仅用于测试的 `choice-probe` 夹具，首版不作为第二款产品注册开放：两名参与者依次用 `game.choose` 从两个符号中选择，双方选完才揭示答案；相同则共同成功，否则共同失败。第一名的选择在第二名行动前不可见，行动发生的事实公开。它不包含棋盘、坐标、棋色或单一赢家。

夹具必须复用同一套建房、授权、动作提交、幂等、暂停、恢复、存储与 AI 调度接口，只增加注册描述、规则、投影和最小 UI。P1 使用固定的内部测试主体驱动双方，不能为测试把 AI 身份伪装入口开放到公网；P2 再验证真实模型参与。

P1 的必测场景：

- 同一套内核契约测试分别运行 gomoku 与 choice-probe，新增模块无需修改房间、鉴权、回执和存储核心；核对核心没有棋盘/棋色假设。
- 游戏 schema 不同但使用同一动作端点；未知类型、跨游戏动作、伪造主体、非法行动顺序、控制动作越权均拒绝。
- 重复、并发、旧版本、同编号不同参数与崩溃恢复遵守统一回执约定；规则异常、非法输出或超额结果不产生半提交。
- 用持久 context 重放随机转换得到相同结果；重复请求不重抽随机数，日志与玩家/模型输出不包含随机材料。
- 用“只改变对方私有选择”的两个状态，验证当前参与者 view、动作提示及对外错误不泄露该差异；检查 SSR、事件、回执和 AI 输入均走投影。
- 暂停、恢复、过期和结束的版本与决策失效一致；不会因轮询或模块返回值绕过平台门禁。
- 加载旧房间只使用精确固定模块；缺失或不兼容模块阻断且保留数据，新规则不能静默接管旧局。
- 第一款游戏完成一局及手机操作验收，choice-probe 覆盖无棋盘、隐藏选择与多人结果。真实多人产品、同时行动和实时游戏另列验收，不由夹具自动宣称支持。

P2 还须对两个模块共用的 worker 路径验证任务去重、迟到动作拒绝、同角色跨房间/跨参与者会话隔离、取消未知状态不重复执行，以及每层重试计入预算。P3/P4 延续 v0.4 的实际手机、换域、观战与短评边界。
