# 让 AI 助手更新 QQ Agents

这份文档写给帮用户更新已部署 QQ Agents 的 AI 助手（Claude Code、Codex、DSH 等能在用户电脑上执行命令的助手）。用户只需要对助手说：

> 请按照这个仓库的 `docs/AI-UPDATE.md`，帮我把现有 QQ Agents 更新到确认的目标版本。保留角色、记忆、配置、登录和权限，先让我确认能力变化与选择，再备份更新，检查通过后等我确认恢复发言。

本文说明由助手执行的手动更新流程。支持的官方安装也可使用 `npm run managed` 和管理台「版本更新」完成备份升级与分阶段恢复，见 [版本更新](UPDATES.md)；没有 `npm run update` 命令。首次安装请看 [AI 安装手册](AI-INSTALL.md)。

## 给助手的规则

1. **更新不是重新安装。** 不运行 `setup init` 或 `setup init --force`，不拿示例覆盖配置，不重建角色、不重置记忆、不轮换令牌。
2. **不读取、打印或复述密钥值。** `secrets.json`、`admin-token`、环境变量文件和登录目录可作为私有备份整体保留，但不得输出内容、上传或提交到 Git。需要新密钥时，由用户本人运行 `setup secret` 输入。
3. **先确认范围，再停机。** 核对安装目录、实际代码目录、实际数据目录、部署方式、目标版本及停机窗口。不把更新框架扩大为更新 NapCat、QQ、Node、Docker、Codex 或 DSH。管理员权限须另行说明并征得同意。
4. **先完成可恢复备份，再让新版打开数据库。** 首次启动可能升级数据库；升级后再备份不能代替升级前备份。
5. **保留角色、会话及连接的原有偏好。** 维护时只操作全局暂停，不修改个别角色或会话的暂停标志。不运行 `setup live --confirm`，它会解除所有角色暂停。
6. **恢复发言必须等用户确认。** 同意更新不等于同意向真实 QQ 会话发言。验收启动不使用 `--resume`，并确保原启动器或服务管理器也不会自动解除暂停。
7. **不强行解决冲突。** 不使用 `git reset --hard`、`git clean`、强制覆盖、删卷或盲删锁。发现本地修改、分叉、未知启动器或无法确认备份时，停下来说明。
8. 各检查阶段运行 doctor，但**不要机械执行 `checks[].fix`**。重新初始化、删除凭据、扩大权限等建议不属于普通更新，必须先诊断。

## 第 1 步：确认现有部署

尽量从现有启动方式确认，不重复索要已经能可靠获得的信息。

| 要确认的           | 说明                                                                                    |
| ------------------ | --------------------------------------------------------------------------------------- |
| 部署方式           | 本机、Docker Compose、macOS `robots.mjs` 或其他服务管理器                               |
| 实际代码目录       | 启动脚本位置不一定等于实际运行代码；可能由 `deployment.json` 的 `codeRoot` 指向发布快照 |
| 实际数据目录       | 本机默认 `.runtime`；`--data` 可覆盖；Compose 示例用命名卷挂载 `/data`                  |
| 当前版本和目标版本 | 记录完整提交 SHA，不只记 package.json 版本号                                            |
| 运行状态           | 全局、角色与会话暂停状态，连接启用状态，启动参数与自动恢复设置                          |
| 本地定制           | 修改源码、Compose 文件、构建参数、未提交文件和外部路径                                  |
| 更新范围           | 只更新 QQ Agents；其他软件升级另行确认                                                  |

在现有源码目录执行：

```sh
git status --short
git branch --show-current
git rev-parse HEAD
node --version
```

核对原启动命令是否还带 `--config` 或 `--port`：外置配置文件也必须备份，实际监听端口可能覆盖配置中的 `port`。下文 setup/doctor 示例仅适用于 `<数据目录>/config.json` 且实际端口与其中 `port` 一致的部署；这两个 CLI 不支持跟随 main 的 `--config`/`--port` 覆盖。自定义部署保留原参数，以实际管理台检查和恢复暂停；不要为使辅助 CLI 通过而把配置改回默认路径或端口。

本机需要 Node.js 24 或更高版本。不符合时先说明，不擅自升级系统软件。读取远端配置时不要把可能含凭据的 URL 输出到对话。

没有 `.git` 的发布快照不适用下文 Git 命令；按原发布来源准备独立新目录，保留原快照，不临时初始化仓库，也不猜版本。

## 第 2 步：固定目标代码，检查变更

先核实 `origin` 是用户授权的代码来源。以下命令只获取代码和准备独立版本目录，不启动服务、不触碰数据。

```sh
git fetch origin
```

将用户确认的分支、标签或版本解析为**完整提交 SHA**；若选择 `origin/main`，记录它此时的完整 SHA：

```sh
git rev-parse --verify 'origin/main^{commit}'
```

阅读该提交中的 `CHANGELOG.md` 和 `docs/MIGRATION.md`，核对数据库变化、配置变化及本地定制兼容性。把目标 SHA 与变化摘要交给用户确认。之后始终用这个 SHA，而不是再次解析可能移动的分支。

在现有仓库中创建新的、此前不存在的发布目录：

```sh
git worktree add --detach "<新的绝对发布目录>" "<已确认的完整目标SHA>"
git -C "<新的绝对发布目录>" rev-parse HEAD
```

核对输出与确认的 SHA 完全一致。新目录应在生产数据目录之外。原目录及本地修改全部保留；若部署依赖修改后的源码，不自动把它们丢掉，也不直接部署上游版本，先确认移植方案。

**不要执行泛用的 `git pull` 后直接上线。** 不把“当前远端最新”当作“已确认目标”。发布快照也应具备可验证的来源与版本，不能手写虚假提交号。

## 第 2.5 步：让用户复核更新后的能力选择（停下来）

按 [安装手册第 6 步](AI-INSTALL.md#第-6-步让用户选择角色能力停下来) 的能力清单介绍可选用途、依赖、费用、隐私和操作范围，但**不执行首次安装的 init/live 流程**。逐角色比较原配置和目标版本的有效配置，列出：原工具列表、显式开启/关闭、未设置字段、目标默认值，以及新增或不再支持的能力。配置比较只报告必要的非敏感字段，不输出整份配置或密钥。

当前目标版本新角色默认使用完整工具目录，多项能力默认开启；旧配置中的显式 `false` 和已有 `tools` 列表保留，**未设置字段可能采用新版默认值**。例如旧角色只保存 8 个工具时，更新不会自动变成完整工具列表；反过来，省略策略字段也不等于用户已同意新增能力。必须在新版第一次运行前识别可能扩大的权限，不能只比较配置文件有没有被修改。

向用户逐项询问：

- 已有能力是否照旧保留？保留现有工具、策略、目录、额度和会话范围，不能一键重置为新角色默认值。
- 新增或原来没配的能力：保持关闭、现在配置，还是以后再说？没有回答不能当作允许；若缺失字段将被新版默认开启，先说明并确认明确的关闭/启用方案，再进入停机和更新。
- 对旧的受限工具列表，是否按用途补充图片、文件、联网、语音等？只添加已选能力，不删除原有选择，也不把所有组一次全开。
- 所选能力需要哪些外部服务、登录、目录、私库、跨群链接及预算？缺依赖时记录“待配置”，不更换后端、不擅自安装软件或获取更高权限。

本步骤先形成用户确认的差异清单。第 4 步完整备份之后、首次启动新版之前，只落实已确认且为防止默认扩权所必需的配置；此时旧服务已经停止，按目标版 schema 在独立配置副本中校验，再按确认方案切换，不为编辑配置偷偷重启旧服务。若需要使用旧管理台，必须另行安排暂停状态下的编辑窗口、再次正常停机并重新取得一致备份。不能确认兼容性就暂停更新，不用 `setup init --force` 重建配置。

新版启动并保持暂停后，再按安装手册的管理台入口落实其余已确认能力，重新打开页面核对保存结果。工具目录、策略开关、后端支持、依赖和会话边界都应检查；不修改全局以外的角色/会话暂停偏好，也不自动增加聊天白名单、授予 L1–L3 或恢复发言。验收分别记录“配置已保存 / 依赖就绪 / 已实测”；真实发送或收费调用另经用户同意。

## 第 3 步：更新前检查，确认停机

本机，在现有代码目录：

```sh
npm run doctor -- --data "<实际数据目录绝对路径>" --json
```

Docker，服务运行时：

```sh
docker compose exec -T qq-agents node src/cli/doctor.mjs --data /data --json
```

记录已有故障。doctor 不发送 QQ 消息，但会访问已配置的 OneBot 和模型服务。`ok: true` 只代表没有 fail，不保证服务运行、模型回合成功或角色能发言；检查 warn 和 skip。

告知用户目标版本、预计中断、备份位置与恢复办法，得到确认后，在管理台“全部暂停”，不改变角色和会话各自的暂停偏好，再正常停止 **QQ Agents**。不停止共享 NapCat、QQ 或 DSH。

Docker，在原项目目录使用原 Compose 项目：

```sh
docker compose stop qq-agents
docker compose ps
```

macOS 已使用项目启动器的部署：

```sh
node scripts/robots.mjs stop --data "<实际数据目录绝对路径>"
```

直接 `npm start` 的部署在原终端正常停止；其他服务管理器按原方式停止，并确认不会自动拉起。不要凭进程名批量结束进程。

## 第 4 步：备份并确认可恢复

备份使用新的私有路径，不放在待更新代码或生产数据目录中。记录并保留：

- 旧代码完整提交、源码本地修改或完整发布快照。
- 整个实际数据目录或 Docker 数据卷，包括配置、数据库、媒体、语音、文件、凭据和角色专用登录。
- 原启动命令、服务管理器设置、Compose 配置、环境变量文件及构建参数。
- 数据目录以外的模型 home、原生 QQ / NapCat 登录及配置路径：记录并保持不变，不删除。仍运行的外部 QQ/NapCat 目录不能靠普通文件复制宣称一致备份；需要备份时使用该组件支持的快照/导出，或另经用户同意安排其停机，不顺带停止共享服务。
- Docker 原运行镜像确切 ID，并为旧镜像保留独立回退标签；验收完成前不清理旧镜像。

所有写入数据的进程必须已停止。不要只复制活跃 SQLite 主文件。

本机源码安装提供数据库一致备份（下面命令在旧源码目录执行，路径指向本机数据；Docker 部署使用本节后面的停机卷备份，不在镜像内运行这个 npm 脚本）：

```sh
npm run memory:backup -- \
  --source "<实际数据目录绝对路径>/memory.sqlite" \
  --destination "<私有备份目录>/memory.before-update.sqlite"
```

目标目录须事先存在，目标文件必须不存在。命令通过 SQLite backup API 包含已提交 WAL 页面，并检查完整性与外键；成功输出应包含 `"integrity": "ok"`。旧安装没有此脚本时，使用已经核实的备份工具或目标代码中的同一只读备份脚本，不为此启动新版应用。

**数据库备份不包含配置、凭据、媒体、语音和模型登录，必须另行备份整套资料。** 备份敏感文件只做本地文件复制，不展示内容；保留权限、归属及所需外部路径。

Docker 应备份实际挂载 `/data` 的卷，而非宿主机 `.runtime`。按 [Docker 备份说明](DOCKER.md#升级与备份) 的停机卷备份方式，将实际卷名和私有归档路径替换正确。卷名前缀随 Compose 项目名变化，不能猜。确认归档可读且包含预期文件，不输出内容。

备份空间不足、失败、无法确认数据位置或恢复办法时，不继续。推荐在独立恢复目录验证备份可用，绝不覆盖生产目录做试验。

## 第 5 步：准备依赖或镜像

### A：本机

在已固定提交的新发布目录：

```sh
npm ci --ignore-scripts
npm run check
npm run doctor -- --data "<实际数据目录绝对路径>" --json
```

不运行启动命令来替代备份验证。配置不兼容时按迁移说明处理，不执行 `setup init --force`。

### B：Docker

**继续使用原 Compose 项目身份、原 Compose 文件所在位置和原数据卷。** 不在新 worktree 中直接运行默认 Compose：这可能创建另一项目或空卷，看起来像数据丢失。

将原 Compose 文件中 `qq-agents` 的构建上下文指向已固定 SHA 的新发布目录；保留现有环境变量文件、卷映射、服务名、端口及其他配置。修改前备份原文件。不要用示例覆盖本地文件，不输出完整渲染配置，以免泄漏环境变量。

构建前确认旧镜像已经独立保留。仍在原 Compose 项目中：

```sh
docker compose build --build-arg SOURCE_COMMIT="<已确认的完整目标SHA>" qq-agents
```

构建上下文须确实是该 SHA 的源码；已有 Chromium 等自定义构建参数一并保留。`SOURCE_COMMIT` 不是随意填写的标签。

本次启动参数移除 `--resume`，保留原有 `--live`、端口等必要参数。原本隔离模式保持隔离。记录临时变化，不擅自扩大功能或权限。

## 第 6 步：启动新版，但不恢复发言

本机沿用原启动方式，明确切换到新代码目录并使用原数据绝对路径。不要让默认 `.runtime` 在新目录中创建空数据。

原本 live、没有额外配置/端口覆盖的直接运行部署，在新发布目录：

```sh
npm start -- --data "<实际数据目录绝对路径>" --live
```

原本隔离模式不加 `--live`。不加 `--resume`。有 `--config`、`--port` 等覆盖的部署继续保留原实际参数。保持进程运行。

macOS 使用项目启动器时，先备份并按现有部署方式将实际 `codeRoot` 指向新版本，保留其他字段，然后：

```sh
node scripts/robots.mjs start --data "<实际数据目录绝对路径>"
```

`robots.mjs start` 还会启动并等待已配置的 macOS 原生 QQ/NapCat，不是纯框架进程启动器；先确认这是原部署预期行为，保持原 `native-profiles.json`，不升级或重建 QQ/NapCat。`robots.mjs` 不是所有系统通用的启动器。其他服务管理器保留原参数，仅切换必要代码路径并关闭本次自动恢复。

Docker，在原 Compose 项目中：

```sh
docker compose up -d --no-deps qq-agents
docker compose exec -T qq-agents node src/cli/doctor.mjs --data /data --json
```

只更新框架服务，不顺带更新 NapCat。不执行 `docker compose down -v`。

核对：

- 实际运行版本与目标提交一致，不能只看磁盘新代码。
- 管理台可访问且保持全局暂停。
- 角色、人设、白名单、权限、连接状态设置，以及角色和会话暂停偏好没有意外变化。
- 历史、记忆、媒体和专用登录仍在，不通过删历史修复问题。
- doctor 无未解释的 fail；warn 和 skip 逐项说明。
- Codex 因实例占用而 skip 时，在管理台检测后端；列出模型不等于完成真实对话验收。

首次打开数据库可能需要迁移时间。出错时保持暂停并保留脱敏诊断，不反复重启、不强杀、不删除 WAL/SHM。排查日志前注意日志可能含私人消息或敏感信息，不把原始日志直接发到公共位置。

## 第 7 步：确认恢复发言（停下来）

列出将恢复的连接、角色和会话范围，以及仍保持暂停的角色，请用户明确确认。更新前原本全局暂停且没有要求上线时，保持暂停即可，不必为了完成更新强行发言。

原本 live 且用户确认恢复的部署，只解除全局暂停。外置配置或端口覆盖部署使用实际管理台，不套用下列 CLI；标准配置路径且端口一致时：

```sh
npm run setup -- unpause --confirm --data "<实际数据目录绝对路径>"
```

Docker：

```sh
docker compose exec -T qq-agents node src/cli/setup.mjs unpause --confirm --data /data
```

`unpause` 会连接已启用的连接、解除全局暂停，并返回各角色 blockers；它不会解除角色各自暂停。不要使用 `setup live --confirm`。

在用户同意的测试会话测试一次真实回复，核对角色、后端及回执，再运行 doctor。不要向所有群广播更新成功。原有自动恢复设置是否恢复，应在验收后按用户明确意愿处理并记录。

## 第 8 步：交付结果

告诉用户：

- 原版本和新版本完整提交。
- 实际更新的代码目录或镜像、实际数据位置。
- 备份位置、验证结果及回退方式。
- 管理台、连接、模型和真实回复各自是否验证。
- 当前暂停状态、保留的个别暂停偏好、剩余警告。
- 逐角色能力差异：哪些沿用、哪些经用户选择新增/关闭、哪些缺依赖，以及各项实际验证范围。
- 自动恢复设置是否临时关闭，以及仍需确认的事项。

没有完成真实回复测试时，只能说“框架已更新并通过对应检查”，不能说“已经确认能聊天”。

## 更新失败时：先停下来，再恢复

1. 保持或恢复全局暂停，正常停止新版，确认没有进程或容器继续写入数据。
2. 将更新后数据及数据库 WAL/SHM 保留到另一私有路径，不覆盖升级前备份。
3. 使用实际旧代码或保留的旧镜像，配套恢复升级前配置、数据库和所需文件。
4. 数据库恢复写入新的不存在路径：

   ```sh
   npm run memory:backup -- \
     --source "<升级前备份数据库>" \
     --destination "<新的恢复目录>/memory.sqlite"
   ```

5. 核对恢复目录的其他文件、权限、归属和启动参数，先在全局暂停状态启动检查；恢复发言仍需用户确认。

数据库结构可能已升级，**只回退代码或镜像并不足够**。旧代码可能拒绝新版数据库，不能强改 schema 版本号。回退应配套使用升级前的一致备份。恢复旧备份可能缺少更新后新增数据，必须告知用户并保留失败现场。

Docker 回退应明确选择已保留旧镜像，并将恢复数据挂载正确，不使用仍指向新镜像的 `qq-agents:local` 标签冒充旧版本，也不让旧镜像直接打开已升级的生产卷。根据实际卷名和部署配置制定恢复命令，不猜测路径或覆盖原卷。

当前没有通用一键回滚命令。无法确认旧代码、旧镜像或升级前备份可用时，保持停止并报告缺项，不宣称已经恢复。

## 常见问题

| 现象                              | 处理                                                       |
| --------------------------------- | ---------------------------------------------------------- |
| 有本地定制或目标与确认版本不同    | 保留原代码，停止部署，重新确认变更及移植方案               |
| 新目录启动后看不到原角色          | 立即停止，核对数据绝对路径或 Compose 项目/卷，不重新初始化 |
| doctor 建议 `setup init --force`  | 不执行；定位配置兼容性问题                                 |
| `DATA_DIRECTORY_LOCKED`           | 核实是否仍有实例写入数据，不盲删锁                         |
| 更新后不说话                      | 先确认是否全局暂停；未确认上线时这是保护状态               |
| `RESTART_WITH_LIVE_FLAG_REQUIRED` | 核对原部署模式和启动参数，不擅自将隔离部署上线             |
| `QQ_NOT_READY`                    | 检查 NapCat、账号和连接；扫码须用户本人完成                |
| 旧代码拒绝数据库版本              | 用升级前备份恢复到新路径，不让旧代码写入升级库             |
